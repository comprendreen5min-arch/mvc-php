1. index() — List users & count stats
GET  /users  →  Users::index()

Fetches the full user list and three separate aggregate counts (total, active, admin-only) using chained queries. All use where('soft_delete', 1) to exclude deleted records.

// Load full user list with selected columns, ordered by newest
$users = $this->mod->table('users')
    ->select('id, first_name, last_name, email, user_role, user_status, created_at')
    ->where('soft_delete', 1)
    ->orderBy('id', 'DESC')
    ->get();

// Count total active users
$totalUsers = $this->mod->table('users')
    ->where('soft_delete', 1)
    ->count();

// Count only active (user_status = 1) users
$activeUsers = $this->mod->table('users')
    ->where('soft_delete', 1)
    ->where('user_status', 1)
    ->count();

// Count admins (user_role = 2)
$adminCount = $this->mod->table('users')
    ->where('soft_delete', 1)
    ->where('user_role', 2)
    ->count();

$this->view('users/index', [
    'users'       => $users,
    'totalUsers'  => $totalUsers,
    'activeUsers' => $activeUsers,
    'adminCount'  => $adminCount,
]);
Why separate count queries? Chaining count() runs a SELECT COUNT(*) SQL query directly — it's more efficient than loading $users and calling count($users) in PHP, especially for large tables. Each query targets a different WHERE condition, so they must be separate chains.
2. store() — Validate & insert new user
POST  /users/store  →  Users::store()
Email uniqueness check before insert

Before creating the user, check whether the submitted email already exists in the database. This is done with a count() chain — no need to fetch the full row.

// Check if email already exists (only count — faster than fetching full row)
$emailExists = $this->mod->table('users')
    ->where('email', $data['email'])
    ->count();

if ($emailExists > 0) {
    $data['email_err'] = 'Email already taken';
}
Insert the new user with insert()

After all validation passes, insert the user using the insert() chain. The password is hashed with PASSWORD_BCRYPT before storing. A unique token is generated via Helper::token().

$inserted = $this->mod->table('users')->insert([
    'first_name'  => $data['first_name'],
    'last_name'   => $data['last_name'],
    'email'       => $data['email'],
    'password'    => password_hash($data['password'], PASSWORD_BCRYPT),
    'user_role'   => $data['user_role'],
    'user_status' => 1,          // active by default
    'soft_delete' => 1,          // not deleted
    'user_token'  => Helper::token(),
    'admin_id'    => $_SESSION['user_id'],
    'admin_name'  => $_SESSION['first_name'] . ' ' . $_SESSION['last_name'],
    'created_at'  => date('Y-m-d H:i:s')
]);

if ($inserted) {
    Helper::flash('user_message', 'User created successfully!', 'alert-success');
    Helper::redirect('users/index');
}
insert() returns true on success and false on failure. Always check the return value to provide feedback to the user.
3. edit() — Fetch a single user by ID
GET  /users/edit/{id}  →  Users::edit($id)

Fetches one specific user object using chained where() filters, then first() to return a single object (not an array). The soft_delete check ensures deleted users cannot be edited.

// Fetch ONE user matching both conditions — returns an object, not array
$user = $this->mod->table('users')
    ->where('id', $id)
    ->where('soft_delete', 1)
    ->first();

if (!$user) {
    // User was deleted or doesn't exist
    Helper::flash('user_message', 'User not found', 'alert-danger');
    Helper::redirect('users/index');
}

// Access properties directly from the returned object:
echo $user->first_name;  // "John"
echo $user->email;        // "john@example.com"
echo $user->user_role;    // 1 or 2
first() vs get(): Use first() when you expect exactly one result (by ID, by unique email, etc.). Use get() when fetching multiple rows. first() returns a single stdClass object or null; get() returns an array of objects.
4. update() — Conditional update with save()
POST  /users/update/{id}  →  Users::update($id)
Check email uniqueness — but exclude the current user

When updating, we need to allow the user to keep their existing email. We exclude the current user's ID using where('id', $id, '!=') — the third argument to where() is the comparison operator.

// Check email exists — but NOT for this user's own ID
$emailExists = $this->mod->table('users')
    ->where('email', $data['email'])
    ->where('id', $id, '!=')  // ← third param is the operator
    ->count();

if ($emailExists > 0) {
    $data['email_err'] = 'Email already taken by another user';
}
Update with where() + update() + save()

The update chain works in three steps: 1) filter with where(), 2) set new values with update([]), 3) execute with save().

// Step 1: where() → filter the target row
// Step 2: update([]) → define the new column values
// Step 3: save() → execute the UPDATE SQL
$updated = $this->mod->table('users')
    ->where('id', $id)
    ->update([
        'first_name' => $data['first_name'],
        'last_name'  => $data['last_name'],
        'email'      => $data['email'],
        'user_role'  => $data['user_role'],
        'updated_at' => date('Y-m-d H:i:s')
    ])
    ->save();

// $updated = true if rows were affected, false if nothing changed
Always include where() before update(). Without it, the UPDATE will affect every row in the table — a catastrophic mistake. The QueryBuilder does not prevent this automatically.
5. delete() — Soft delete a single user
POST  /users/delete/{id}  →  Users::delete($id)

A soft delete sets soft_delete = 0 on the row — it does NOT run a SQL DELETE. The user's data remains in the database and can be recovered. A self-deletion guard prevents logged-in admins from deleting their own account.

// Safety guard: admin cannot delete their own account
if ($id == $_SESSION['user_id']) {
    Helper::flash('user_message', 'You cannot delete your own account', 'alert-warning');
    Helper::redirect('users/index');
}

// Confirm user actually exists before deleting
$user = $this->mod->table('users')
    ->where('id', $id)
    ->where('soft_delete', 1)
    ->first();

if (!$user) {
    Helper::flash('user_message', 'User not found', 'alert-danger');
    Helper::redirect('users/index');
}

// Soft delete: sets soft_delete = 0 (does NOT run SQL DELETE)
$deleted = $this->mod->table('users')
    ->where('id', $id)
    ->softDelete();

// $deleted = true on success
softDelete() vs hardDelete(): softDelete() runs UPDATE users SET soft_delete = 0 WHERE id = ?. The record stays in the DB and is excluded from future queries that filter where('soft_delete', 1). A hardDelete() would run a real DELETE FROM users WHERE id = ? — permanent and irreversible.
6. toggle_status() — AJAX status toggle
AJAXPOST  /users/toggle_status/{id}

An AJAX endpoint. Fetches only the user_status column (efficient), flips the value (0 ↔ 1), then saves it. Returns a JSON response so the frontend can update the UI without a page reload.

// Fetch only the status column — no need to load the full row
$user = $this->mod->table('users')
    ->select('user_status')        // only fetch what you need
    ->where('id', $id)
    ->where('soft_delete', 1)
    ->first();

if (!$user) {
    echo json_encode(['success' => false, 'message' => 'User not found']);
    return;
}

// Flip the value: 1 → 0, 0 → 1
$newStatus = $user->user_status == 1 ? 0 : 1;

// Save the toggled value
$updated = $this->mod->table('users')
    ->where('id', $id)
    ->update(['user_status' => $newStatus])
    ->save();

// Return JSON for the AJAX caller
echo json_encode([
    'success'    => true,
    'message'    => 'Status updated successfully',
    'new_status' => $newStatus    // frontend uses this to update the UI
]);
Tip: Use select('column1, column2') to fetch only the columns you need. For a toggle, fetching only user_status is far more efficient than loading all 15+ columns of the user row.
7. search() — whereLike() fuzzy search
POST  /users/search  →  Users::search()

whereLike() generates a LIKE SQL clause. The % wildcard is applied manually around the search term. This example shows a cascading search: first tries first name, then last name, then email as fallbacks.

$search = trim($_POST['search']); // e.g. "john"

// Step 1: Search by first name
$users = $this->mod->table('users')
    ->select('id, first_name, last_name, email, user_role, user_status, created_at')
    ->where('soft_delete', 1)
    ->whereLike('first_name', "%{$search}%")  // SQL: first_name LIKE '%john%'
    ->orderBy('first_name', 'ASC')
    ->get();

// Step 2: If no results, try last name
if (empty($users)) {
    $users = $this->mod->table('users')
        ->where('soft_delete', 1)
        ->whereLike('last_name', "%{$search}%") // SQL: last_name LIKE '%john%'
        ->orderBy('last_name', 'ASC')
        ->get();
}

// Step 3: If still nothing, try email
if (empty($users)) {
    $users = $this->mod->table('users')
        ->where('soft_delete', 1)
        ->whereLike('email', "%{$search}%")    // SQL: email LIKE '%john%'
        ->orderBy('email', 'ASC')
        ->get();
}
Performance Note: LIKE '%value%' with a leading % cannot use a database index and will perform a full table scan. For small tables this is fine; for large datasets, consider a full-text search index.

9. by_role() & by_status() — Multi-condition filters
by_role($role) — Filter users by their role
GET  /users/by_role/2  → shows all admins

Chains two where() conditions: one for active records (soft_delete = 1) and one for the role. Multiple where() calls are joined with AND.

// GET /users/by_role/2 → shows admins
// GET /users/by_role/1 → shows regular users
$users = $this->mod->table('users')
    ->select('id, first_name, last_name, email, user_role, user_status, created_at')
    ->where('soft_delete', 1)   // AND
    ->where('user_role', $role) // AND (multiple where = AND)
    ->orderBy('first_name', 'ASC')
    ->get();
by_status($status) — Filter by active / inactive
GET  /users/by_status/0  → shows inactive users
// GET /users/by_status/1 → active users
// GET /users/by_status/0 → inactive users
$users = $this->mod->table('users')
    ->select('id, first_name, last_name, email, user_role, user_status, created_at')
    ->where('soft_delete', 1)
    ->where('user_status', $status)
    ->orderBy('created_at', 'DESC')
    ->get();

$statusName = $status == 1 ? 'Active Users' : 'Inactive Users';
Multiple where() = SQL AND. Every additional ->where() call appends an AND to the WHERE clause. So ->where('soft_delete', 1)->where('user_role', 2) compiles to WHERE soft_delete = 1 AND user_role = 2.
10. bulk_delete() — whereIn() for multi-row operations
AJAXPOST  /users/bulk_delete

whereIn() matches a column against a list of values — equivalent to SQL WHERE id IN (1, 4, 9, 12). This makes it perfect for bulk operations on a set of selected records from a DataTable.

// Frontend sends: ids = "[1, 4, 9, 12]" (JSON string from checkboxes)
$ids = json_decode($_POST['ids'], true); // → [1, 4, 9, 12]

// Guard: prevent admin from bulk-deleting themselves
if (in_array($_SESSION['user_id'], $ids)) {
    echo json_encode(['success' => false, 'message' => 'Cannot delete your own account']);
    return;
}

// whereIn() → SQL: WHERE id IN (1, 4, 9, 12) — efficient single query
$deleted = $this->mod->table('users')
    ->whereIn('id', $ids)   // ← pass an array of IDs
    ->softDelete();

echo json_encode([
    'success' => true,
    'message' => count($ids) . ' users deleted successfully'
]);
whereIn() is far more efficient than a loop. One query with WHERE id IN (1,4,9,12) is always faster than running four separate WHERE id = ? queries in a PHP loop. Use it whenever you need to act on a selected set of IDs.
11. get_users_data() — DataTables SSP with formatters
GET/users/get_users_data

Returns a server-side processed JSON response for jQuery DataTables. The $columns array maps database columns to DataTable column indices (dt). Some columns include formatter closures to transform raw values into HTML badges or action buttons.

$columns = [
    // dt: 0 → first_name column (plain text, no formatter)
    ['db' => 'first_name', 'dt' => 0],

    // dt: 1 → last_name column (plain text)
    ['db' => 'last_name',  'dt' => 1],

    // dt: 2 → email column (plain text)
    ['db' => 'email',      'dt' => 2],

    // dt: 3 → user_role — formatter converts 1/2 to HTML badge
    [
        'db' => 'user_role', 'dt' => 3,
        'formatter' => function($d) {
            return $d == 2
                ? '<span class="badge bg-success">Admin</span>'
                : '<span class="badge bg-primary">User</span>';
        }
    ],

    // dt: 4 → user_status — formatter renders icon
    [
        'db' => 'user_status', 'dt' => 4,
        'formatter' => function($d) {
            return $d == 1
                ? '<i class="fa fa-check-circle text-success"></i>'
                : '<i class="fa fa-times-circle text-danger"></i>';
        }
    ],

    // dt: 5 → id — formatter renders Edit + Delete action buttons
    [
        'db' => 'id', 'dt' => 5,
        'formatter' => function($d) {
            return '
                <a href="' . URLROOT . '/users/edit/' . $d . '" class="btn btn-sm btn-warning">
                    <i class="fa fa-edit"></i>
                </a>
                <button class="btn btn-sm btn-danger delete-btn" data-id="' . $d . '">
                    <i class="fa fa-trash"></i>
                </button>
            ';
        }
    ]
];

// dataTable() handles pagination, search, ordering, and JSON output
echo $this->mod->dataTable('users', $columns, 'user_role = 1');
The third argument to dataTable() is an optional raw SQL WHERE string ('user_role = 1') that pre-filters the dataset before DataTables applies its own search and pagination. Use this to scope the table to a specific subset of records.
The id column should always be the last entry in the $columns array when used for action buttons. This is because DataTables renders columns left-to-right; placing id last ensures it's only used for the actions column without rendering a visible ID number.
